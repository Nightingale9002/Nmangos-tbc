## 协作纪律（站长定，2026-10-04；违反即为沟通事故）

> 背景：2026-10-03 排查"游泳怪在水面走路"时，我（AI）连续用未经证实的猜测反复改代码、反复重启，

> 还把站长一句疲惫的顺口回应当成"修好了"的证据写进手册，前后烧掉大量 token 与站长的时间。

> 结论：真因（create 包里多带了一条内嵌 spline 顶掉客户端的游泳判定）本来在解码客户端抓包后一轮就能定案。

### 一、不许制造验证

没有自己解码出来的客户端包（或等价的一手证据），就不写"已修复 / 已验证"，只写"改了 X，尚未验证"。

不把结论塞进问题里做引导性提问。要问就要求对方描述可观测的具体项，并允许对方回答"没看 / 不知道"。

对方的回话如果不是自发、具体的观察（只是重复我的措辞、顺口答应），一律记为"未验证"，

不写进任何文档的验收段。

### 二、一次只动一个变量

一个假设等于一次改动加一次测量。测量优先用我自己能读的数据（抓包、日志、库表），

需要站长游戏内观察时，一次把要看的项全部问完，不来回要人看。

上一个改动没被证实就先回滚，再谈下一个，不叠加未验证的行为改动。

### 三、两次不收敛就停

同一个问题，连续两次"改了但没解决"之后必须停下来，给出选项（继续查 / 回滚 / 搁置）并说明各自代价，

不再自行试第三次。

### 四、不误导性汇报

汇报里区分"我做了什么"和"事实是什么"；结论句必须能指到证据（日志行、包字节、库表值）。

对方的批评如果指向前几轮的错误，先承认再往下走，不解释成"运气不好"。

### 五、给站长的成本意识

编译加重启一次的代价包含站长必须重新登录、重新跑测试。能靠离线数据（抓包、离线地图探针、库查询）判断的，

不要用"改代码看效果"来试。

## 〇、KNOWN_ISSUES.md 章节书写规范（新增/改动章节时照着来）

- **章节标题**：`## [分类] 名称 — YYYY-MM-DD 状态`；状态用「已修（本地/云端）」「待修」「分析，未改」「搁置」等明确词。
- **分类词表**（**已在使用，优先复用；要造新词先跟站长确认**）：
  `[地图] [机制] [寻路] [内存] [任务] [水移动] [资源] [平衡] [数据] [配置] [天赋] [部署] [稳定性] [战术] [性能] [待办]`
  `[修复] [本地化] [运维] [经济] [掉落] [核心] [技术]`
- **章节内部建议结构**：`### 现象` → `### 定位/根因（带证据：库字段值、源码文件:行号、日志原文）` → `### 修复（对应 SQL/代码文件）` → `### 验证（本地测了什么、云端是否已部署）` → `### 待办/残留风险`
- **必须留证据**：涉及"是谁的问题"的结论要写清 ID 命名空间（生物 entry / GO entry）、源码位置、日志原文，避免后人重复排查或反向"修错"。
- ⚠️ 本文件**随源码提交 git**：**不要写**云端 IP、SSH 密钥路径、数据库密码等敏感信息（那些留在本地 handoff）。
- **新增章节后同步本文件的第二节章节索引表**（行号会随插入漂移，只作定位提示，不必强求精确）。
