### 2. 本 fork 任务"学会技能"机制（关键，踩坑记录）

- **语义（用户确认）**：RewSpell = **任务让角色学会的法术**（写进技能书的那个）；RewSpellCast = **对玩家释放一次的法术**。
- **本 fork SPELL_EFFECT_LEARN_SPELL = 36**（不是标准的 53！见 src/game/Spells/SpellEffectDefines.h:62）。
- 学会发生在"释放载体法术"时：Spell::EffectLearnSpell 读 **EffectTriggerSpell**（SpellEffects.cpp）→ player->learnSpell。
- 任务奖励流程（Player.cpp RewardQuest，~13516 行）：
  - spellId = RewSpellCast; if (!spellId) spellId = RewSpell; 然后对玩家 CastSpell(spellId, TRIGGERED_OLD_TRIGGERED)
  - 即：有 RewSpellCast 就释放 RewSpellCast（载体）；没有才退而释放 RewSpell。
- **正确设计（方案 A）**：RewSpell = 31892/31801（学会的圣印本体，客户端原生显示"你学会了"）；RewSpellCast = 91010/91011（载体，Effect1=36 + EffectTriggerSpell1=圣印），释放一次触发学会。
- 骑术示例：RewSpell=33388（学会的骑术）、RewSpellCast=33389（载体，Effect1=36+Trigger=33388）→ 施放 33389 学会 33388。
- 库内另一变体（种族技能任务）：RewSpell=19338（载体本身带 36 效果）、RewSpellCast=0 → 退而释放 RewSpell，学会其 EffectTriggerSpell=13908。此变体把载体放 RewSpell，奖励图标显示 19338（客户端 DBC 存在所以正常）；自定义载体放 RewSpell 则图标"未知"→ 所以圣印任务用方案 A（载体放 RewSpellCast）。
- TRIGGERED_OLD_TRIGGERED 施放**不发客户端动画** → 载体法术对客户端完全不可见，无显示瑕疵。

### 矿脉刷新加速（2026-09）

> **目的**：加快矿脉（铜/锡/金/铁/秘银/真银/瑟银/外域矿脉等）刷新频率。

- **机制**：矿脉通过 spawn_group 占位系统生成（416 个矿脉组，含全部变体）。刷新时间由 spawn_group 的 `RespawnOverrideMin/Max` 控制（SpawnGroup.cpp:80，组空时用 override 调度），无 override 时用占位点 `spawntimesecs`（主流 600s，78 个 604800s=7 天坑）。
- **改动**：038 SQL 给全部矿脉组设 `RespawnOverrideMin=300, RespawnOverrideMax=600`（5-10 分钟随机刷新），只影响矿脉组（不动草药占位点），并覆盖 7 天坑。
- **生效**：本地已应用（416 组）；云端已改库，**待云端重启 mangosd 生效**。
- **注意**：respawn 时间持久化在 characters 库 `gameobject_respawn`，重启不会清除/重置矿脉（未挖的立即重生，挖掉的按剩余时间）。

### 竞技场赛季事件管理（GameEvent 53-56）

> 竞技场赛季在 CMaNGOS 中实现为 **GameEvent**（Arena PvP Season 1-4）：
> **53 = S1、54 = S2、55 = S3、56 = S4**。每个赛季事件刷出对应赛季的竞技场军需官
> （如 28225 Griz Gutshank 由 event 56 刷出）。控制事件启停 = 控制竞技场装备是否开放。

- **为什么之前停不住**：`game_event` 表用 `schedule_type` 字段（原 53-56 = `1`/DATE），
  按 `game_event_time` 表每年周期**自动开启**。GM `.event stop 56` 只改运行时内存状态、不写库，
  **服务器重启后 56 又按时间自动重新开启**（`GameEventMgr.cpp` `LoadFromDB`/`Update`）。
- **关闭方案（已应用 2026-09）**：把 53-56 的 `schedule_type` 改成 **0 = GAME_EVENT_SCHEDULE_SERVERSIDE**
  （dev/037_关闭竞技场赛季事件.sql）。该类型加载时把事件 start/end 置 FAR_FUTURE，服务器运行中
  `Update()` 直接跳过、不自动开/关；重启后 `CheckOneGameEvent` 对 FAR_FUTURE 恒返回 false → 事件不开启、
  军需官不刷出。**只在 GM 手动 `.event start <id>` 时才出现。**
- **操作命令**：
  - `.event stop <id>` / `.event start <id>`（id=53/54/55/56）手动停/开对应赛季。
  - 已停 56（S4）。当前 53-56 全部 `schedule_type=0`，重启也不会自动开。
- **风险/待确认**：
  - 竞技场军需官（26305/26308/26309）ExtendedCost=0，购买无竞技场点数门槛，可能白送 S1-S3 及团本 151 装等。
  - 26305/26308/26309 无 spawn 模板仍卖竞技场装——若军需官本身被刷出，存在白送风险；关闭事件（不刷军需官）是最直接的规避。
  - 当前策略：前期不开放竞技场装备（事件关闭）。

### 生命绽放结算按层数修复（2026-09）

> **现象**：德鲁伊生命绽放（Lifebloom 33763）最终结算治疗恒为「一层」的量，叠满 3 层结算量不变。

- **根因**（上游 bug，非本 fork 引入，blame 为 Laise/VladimirMangos/killerwife 等上游提交）：
  - 33763 = HoT（Effect1/PERIODIC_HEAL，base 38）+ dummy（Effect2/SPELL_AURA_DUMMY，base 599），StackAmount=3，SpellFamilyFlags=0x1000000000。
  - 最终结算由 dummy 效果在移除时施放 33778（直接 HEAL）完成。
  - `SpellAuras.cpp` `HandleAuraDummy` 内 Druid 分支（仅匹配 0x1000000000，数据库确认只有 33763 命中，无其他技能受影响）：
    - apply 分支 `m_modifier.m_amount /= GetStackAmount()` → 恒存**单层量**（叠加到 N 层 amount 仍是单层基础量×加成，因叠加时 `SetStackAmount` 算 `stack×base` 后又走 apply 分支除以 stack）。
    - 结算分支 `int32 amount = m_modifier.m_amount;` **没乘层数** → 恒为单层量。
- **修复**（SpellAuras.cpp:2911）：
  ```cpp
  // 原：int32 amount = m_modifier.m_amount;
  int32 amount = m_modifier.m_amount * GetStackAmount(); // 结算 = 单层量 × 当前层数
  ```
- **影响范围核验**：命中 flag 的仅 33763；改动只在 dummy 效果（HoT 走 HandleAuraPeriodicHeal 不受影响）；33778 仅此一处 cast，无双倍结算；33763 无自定义 spell script 覆盖。
- **行为**：3 层到期结算 3×单层量；驱散（AURA_REMOVE_BY_DISPEL）逐层递减时按剩余层数结算。
- 状态：代码已改，待编译/云端部署验证。

### 定身怪物攻击近战目标修复（Bug2，2026-09）

> **现象**：怪物被定身（如冰环）后，即使玩家站在近战范围内也不攻击（威胁列表里的近战目标也不打）。

- **根因**（上游/既有代码，调用链逐行核实）：
  1. `DoMeleeAttackIfReady`（UnitAI.cpp:302）第一行闸门要求 `UNIT_STAT_MELEE_ATTACKING` 置位才会调用 `UpdateMeleeAttackingState`——而"定身怪攻击近战"的 swap 逻辑（0173de658，Unit.cpp UpdateMeleeAttackingState）只在该函数里；
  2. 远程怪分支（UnitAI.cpp:1128-1129）在 victim 够不到时每帧 `MeleeAttackStop` 清 MELEE_ATTACKING → swap 永远不执行；近战怪若 MELEE_ATTACKING 从未置位同样短路；
  3. `selectNextVictim` 的"定身跳过远程目标"分支（ThreatManager.cpp:339/360/381）依赖 `IsIgnoringRangedTargets()`，它默认 false、只在 `SetCurrentRangedMode`（远程↔近战切换）设置；`SetImmobilizedState` apply 分支没设置（解除时 10664 才设 false，不对称）→ 定身怪 victim 仍是远处目标。
- **修复**（3 处配合 + 诊断日志）：
  1. `Unit.cpp SetImmobilizedState` apply 分支：非玩家控制时 `SetIgnoreRangedTargets(true)` → 定身时 `selectNextVictim` 真正生效，victim 重定向到近战范围目标；
  2. `UnitAI.cpp DoMeleeAttackIfReady`：放宽闸门 `MELEE_ATTACKING || (非玩家 && IsRooted && GetVictim())` → 即使 MELEE_ATTACKING 被清/未置位，swap 也能跑；
  3. `UnitAI.cpp` 1126-1132：定身怪跳过 `MeleeAttackStop`（避免每帧清状态+动画抖动）；
  4. 诊断日志 `[BFDBG]`（aura 10909 门控）用于实测定位，**测试通过后已清除**（保留修复逻辑，无日志）。
- **Bug1（变友善不脱战）**：重新测试无问题，未做额外改动（当前代码已含相关兜底）。
- **后续实测反馈修复**（2026-09，测试通过）：
  - 无近战目标时：`selectNextVictim` 在 suppressRanged 下返回 null → `SelectHostileTarget` 清空 m_attacking → 怪失目标。修复：suppressRanged 且无近战目标时回退第一仇恨（面向它，不攻击）；
  - 缠绕结束后不切回第一仇恨：`ThreatContainer::update` 只在 `iDirty||force||isPlayer` 时重排，定身（force=true）近战优先排序在解除后不刷新。修复：force（IsIgnoringRangedTargets）变化时强制重排（`m_lastForce`）。
- 状态：本地测试通过，日志已清除，待提交/云端同步。

### 实测发现（2026-08-21，穿门补丁客户端）
- **客户端自带防修改检测（farmdoor 诱饵）**：穿门补丁客户端进游戏触发
  `ERROR #131 (0x85100084) File: world\generic\...\farmdoor01test.m2` → 客户端弹窗"Press OK to terminate"并**自行终止**。
  - `farmdoor01test.m2` 是补丁作者/客户端埋的**诱饵检测文件**：正常客户端不会加载它，修改过碰撞的客户端在某区域被触发加载
    → 文件缺失 → 客户端进程内报错自杀。这是**客户端侧机制，与服务器无关**（服务器检测到作弊的表现是踢线，不是客户端弹窗）。
  - 结论：穿门补丁客户端若进游戏前就弹窗终止，服务器端无需处理（它玩不了）；能绕过的话由服务器 Warden/Movement 兜底。
- **客户端无法学习新增技能 = 同类客户端机制（用户确认推断）**：殉难圣印 20000 客户端显示坏、跨阵营圣印训练师不可学，
  根源都在**客户端自身**（Spell.dbc 数据缺失 / 训练师 UI 的 SkillLineAbility.dbc 阵营判定），服务器改不了客户端行为
  → 只能绕开（任务线学技能，即本手册第一章方案二）或客户端打补丁。这与 farmdoor 同属"客户端黑盒"范畴。
- **此前掉线玩家归因（用户确认）**：掉线玩家使用**其他版本客户端**（无法正确回复 Warden 协议/版本不兼容），
  与 b501fb3d 超时踢人→不踢 的修复归因一致；现在超时不踢后这类客户端只会扫描失效，不再掉线。

### Warden 机制澄清（2026-08-21 修正，重要）
> 用户最初理解："反作弊内置 warden 默认开启、检测客户端版本、无 warden 模块被踢、开 warden 后篡改客户端无法游戏"。
> 以下为修正后的准确机制，决策（是否开云端 Warden）以此为准。

1. **Warden 不是默认开启，由配置控制**：`anticheat.conf` 的 `Warden.Enable` 决定——**本地=1（开）、云端=0（关）**。
   `Enable=0` 时 `_warden=nullptr`（libanticheat.cpp `GetWardenEnabled()` 分支），Warden 完全不初始化。
2. **Warden 检测的是客户端完整性，不是版本**：服务器下发加密 .bin 模块，客户端运行后回传校验结果，
   比对 hack 特征（内存扫描 + 文件校验 + EndScene hook 检测）。**客户端版本/build 检查是登录阶段的另一套机制**
   （realmd/World 登录时校验 build），与 Warden 无关。其他版本客户端跑不了模块，表现为"无法回复"，不是"版本检测"。
3. **无法回复 Warden 的客户端不会被踢（b501fb3d 已改）**：旧代码超时 30 秒 KickPlayer 踢线；
   现改为只记录 `"timeout (not kicked)"` + 停止该会话扫描（warden.cpp:495-500）。扫描失效不等于踢线。
4. **"开 Warden 后篡改客户端无法正常游戏"部分成立**：带作弊特征的篡改客户端（穿门/飞行/加速补丁命中扫描）会被踢
   （作弊检测路径 KickPlayer 与超时无关）；**其他版本/无法回复的客户端不踢**（仅扫描失效）。

| 客户端类型 | 服务器反应（当前代码）|
|---|---|
| 官方 2.4.3 客户端 | Warden 正常扫描，无作弊 → 正常游戏 |
| 被篡改且带作弊特征 | Warden 扫描命中 → 踢（作弊检测路径）|
| 其他版本 / 无法回复 Warden | 不踢（超时不踢），仅记录 + 扫描失效 |
| 客户端内置诱饵检测（farmdoor） | 客户端自己弹窗终止，服务器不参与 |

→ **云端开 Warden 安全**：正常玩家不掉线；作弊客户端被扫描命中踢线。
